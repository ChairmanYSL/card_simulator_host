## 0. 目的与范围

把 host / 卡端 / POS 三方从 v1.2 硬切到 **协议 v2（CTEL2 TEI）** 后的第一轮联调跑通，并约定
"**统一测试 → 统一修改 → 再统一复测**"的协同规则。卡端仅测非接（contactless），不做接触。

## 1. 本轮协议变更要点（三方必读）

| 项 | v2 行为 |
| --- | --- |
| 信封 / 握手 | 信封 `v=2`；握手 `protocol_version="2.0"`，缺失或 `<2.0` → 拒绝。（**新增**）入站帧 `v != 2`：握手期 `bad_frame` 拒绝，运行期告警并断开 |
| POS 报文 | `test_info` → `config`（仅当该用例有内核参数）→ `act`，逐个等 `*_ack`（`ResponseCode=YES`）；POS 回 `out`（OPS + DataRecord） |
| **已删除** | `config_push{device_config/pos_config/pos_kernel_config}`、`case_started`、`transaction_result`、`session_abort`。**硬切换，无兼容开关** |
| **中止无通知帧** | `session_abort` 已删：无论正常跑完还是 ABORTED/STOPPED/ERROR，host **都不再**向卡端或 POS 发通知帧；卡端仍走 `stop_emulation` 收尾 |
| CONFIG 形态 | 同名 id **逐条**（非数组）；`DRL` / `EXCEPTION_FILE` **每笔恒发**，空表发一条 `value:""` = "清空该表且不加"；id 缺失 = 不管理该表 |
| 判定时机 | host **先判定并落盘，再回 ack**；POS 的 ack 含义 = "判定已落盘"。重复 `msg_id` 回 `duplicate` 不重判；无主 OUT 进 `quarantine.jsonl` |
| `resp_code` | 优先 `DataRecord.8A`；无 8A 再按 OPS Status（APPROVED→`00` / DECLINED→`05` / ONLINE REQUEST→`00`）；**内核未跑**（OPS 全 0 + 空 DataRecord）→ 用例 FAIL `out_no_outcome`，host 不伪造 `05/91/80` |
| 卡端链路 | 不变：`config_push{card_config}` / `start_emulation` / `stop_emulation` / `status` / `log`（+心跳） |
| 失败原因码 | 全表见 `docs/protocol.md` §12.3（`test_info_*` / `config_*` / `act_*` / `pos_not_connected` / `out_timeout` / `out_no_outcome` / `card_*` / `android_*` …） |

## 2. 前置条件（preflight —— 缺一不开跑）

1. **两端在线**：`/api/health` 中 `devices.android.connected = true` 且 `devices.pos.connected = true`；
   卡端装完后通常需在 Test 页点一次 **Connect** 才会连上 host。
2. **版本一致**：两端 `app_version` 必须与 `--expect-versions` 完全一致，否则**拒绝开跑**（退出码 2）。
3. **host 可达**：POS 与卡端均按现场配置指向 host 的 9100（device 口）与 8000（web 口）；
   token 取仓库 `tokens.json` 中对应 `client_type` 的值（**不写进任何文档/报告**）。
4. **静态包**：`frontend/dist` 需为**本次构建**产物（`cd frontend && npm run build`）。
   ⚠️ 本轮前该目录长期是 2026-09-15 的陈旧包（构建曾被两个既有缺陷阻断，已修，见 `docs/CHANGELOG.md` 2026-09-18 前端条）。
5. **无人在跑**：确认没有其它会话/进程占用 runs、没有残留 host 进程（`runs/.host.lock` 不应为活 PID）。

## 3. 轮次门控（沿用 `AGENTS.md` §3）

- host 是统筹，卡端与 POS 是执行方：**只在两端都明确 `[READY]` 后发起 run**；单方就绪不开跑。
- **一轮只跑一次**；run 期间两端**不装、不重启**。
- 任一端需要改动 → 先发 `[PAUSE-REQ]`，host 回 `[PAUSE-ACK]` 后才动手；改完各自 `[READY]` 再复跑。
- 一律用 `session-link` 通信（工具 `session_link_list/send/reply/status`）：每次先列会话取 id（不凭记忆沿用旧 id）；
  关键消息带 `request_reply=true` 并用 `session_link_status` 核对落点。

## 4. 统一测试修改流程（三方）

1. **一轮一次**：host 下发 run → 两端各自取证 → 汇总到 host → 判定 → 若要改，走 §3 的 PAUSE 流程。
2. **归因纪律**：只用**双侧证据交叉**——卡端以 logcat **timestamp** 为准（先校准时钟偏移）+ POS 内核 `retcode`；
   **不得用事件顺序推断因果**（field 事件同步、APDU 事件滞后）。同一错误码**每轮重新取证**，标明"直接观测"或"推断"。
3. **产物分文件**：脚本产物与人工分析分开；mock 与真机结果分目录并显式标注环境。
4. **不落"定稿/已实施"**：协议/版本等易变项写**带时间戳的状态轨迹**；未在设备上落地前不下结论。
5. **范围**：host 只改本仓库；对端改动**只通过通知文档**交付（v2 通知见 `docs/change-notice-v2-pos.md` /
   `docs/change-notice-v2-card.md`）。
6. **结论以落盘为准**：JSON / trace / logcat 为准，不用消息叙述当证据。

## 5. 阻塞处理

- 物理/环境阻塞（设备掉线、断电、无调试通道）**一次讲清恢复条件**；同一条件连续 ≥2 轮无变化即上报
  "需人工介入"，不逐轮重复播报。
- 设备异常先 `adb kill-server && adb start-server` 复核；判定 app 状态用 `dumpsys activity/package`，不用 `ps | grep`。

## 7. 证据与安全口径

- run 产物：`runs/<run_id>/`（`results/<case_id>.json`、`trace/<case_id>.jsonl`、`quarantine.jsonl`、`checkpoint`）。
- 证据收集：host 侧 run JSON + 两端日志；卡端 logcat 过滤采集；POS 内核 `retcode`。
